## 2.1 GroundPlaneAnalyzer — untested_threshold: RANSAC + plane-fit thresholds

**Файл**: lib/utils/ground_plane_analyzer.dart:12-23, 124, 162

**Сценарий**: A6 (noisy depth / low light)

**Ожидание** (prompt): uniform depth noise → `lastPlaneFitOk == false` →
plane-independent hazards path.

**Факт**: The five prompt-listed constants have **no inline rationale comments**:

| Const | Value | Line | Rationale comment? |
|-------|-------|------|--------------------|
| `kRansacIters` | 40 | 12 | none |
| `kInlierThresh` | 0.15 | 13 | none |
| `kDropRatio` | 0.30 | 15 | none |
| `kFootZoneDeltaThreshold` | 0.32 | 19 | none |
| `kReflectiveInlierRatioMin` | 0.88 | 22 | none (purpose documented at usage :48-56, not threshold derivation) |

Worse, the harness (A6) shows `planeFitOk == true` on uniform noise
(`Float32List` filled with `Random(42)` values in [0.1, 0.9]). The plane-fit
acceptance bar is `maxInliers >= _pointCount * 0.2` (GPA:162) with
`kInlierThresh = 0.15` **relative** error. A horizontal plane at z≈0.5 captures
all points with z ∈ [0.425, 0.575] ≈ 18.75 % of a [0.1, 0.9] uniform
distribution; a lucky tilted 3-point sample over 40 RANSAC iterations readily
exceeds the 20 % bar. Result: the `planeOk = false` branch (GPA:169-173,
delegates to `_appendPlaneIndependentHazards`) is **effectively unreachable for
any non-sparse input**. The only sub-10-point early return (GPA:124) does NOT
set the flag either — it keeps `_lastPlaneFitOk` at its default/previous value
(GPA:72), so even the sparse case never reports `planeFitOk = false`.

**Гипотеза**: In low light MiDaS produces noisy depth; with these thresholds the
analyzer runs the plane-based drop/rise scan on a *spurious* plane. Consequences
cut both ways and are safety-relevant: (a) a garbage plane can "absorb" a real
drop → missed hazard; (b) noise aligned with the spurious plane can emit
spurious drop/rise → alert spam. Either is a blind-user physical-harm risk.

**Тип**: risk (classified up to Critical-adjacent due to physical-harm
ambiguity — low-light false negatives OR false positives on the primary
ground-hazard path). The thresholds themselves are `untested_assumption` (no
documented field-test derivation).

**Solution (NOT applied — diagnosis only)**: Add rationale comments to each
constant; consider raising the inlier bar (e.g. `maxInliers >= 0.35 * count`)
or tightening `kInlierThresh`, and set `_lastPlaneFitOk = false` on the
`_pointCount < 10` early return so the degradation flag is honest. Do NOT touch
`alert_filter.dart` or the pipeline order.

## 2.1b GroundPlaneAnalyzer — risk: walking gate is bypassed by pit-gradient fallback

**Файл**: lib/utils/ground_plane_analyzer.dart:256-257, 424-437, 744

**Сценарий**: A2 (foot-zone drop, walking)

**Ожидание**: a foot-zone drop with coverage 0.30 is below
`kWalkingMinCoverage = 0.38`, so while walking `_passesWarningGate` (GPA:80-89)
should suppress the plane-based drop hazard.

**Факт**: The plane-based drop IS gated out while walking (`hazardsWalk` has no
plane-scan center drop → `hasCenterDrop = false`, GPA:424-429). But the
pit-gradient fallback `detectPitGradientFromMap` (GPA:433, impl :744) then runs
(`!hasCenterDrop && !_weatherDegradedHint`) and flags the 0.5→0.05
discontinuity as a pit/pothole. So the foot-zone drop **is still reported while
walking**, via a second path. Harness A2 confirms `walkingDetectsDrop = true`.

**Гипотеза**: This is a safety-positive redundancy (the drop survives the
walking gate), but it means `kWalkingMinCoverage` does NOT actually gate
foot-zone drops in practice — the fallback re-opens the door the gate closed.
The two paths are not coordinated; tuning `kWalkingMinCoverage` to reduce
walking false positives would have no effect on foot-zone drops because the
pit-gradient path ignores it.

**Тип**: risk (uncoordinated gating; tuning surprise). Not a bug — outcome is
safe (drop detected), but the constant's stated purpose is partially defeated.

## 2.2 camera_screen — verified_safe: `_isDetecting` flag is try/finally guarded

**Файл**: lib/camera_screen.dart:85, 1590, 1621, 1628, 1820-1822

**Сценарий**: 2.2 (race condition in `_isDetecting`)

**Ожидание** (prompt hypothesis): an exception in the pipeline could leave
`_isDetecting = true` forever → all future frames dropped.

**Факт**: The flag is set `true` at :1621 immediately before a `try {` block
(:1628) and reset `false` inside a `finally` block (:1820 `} finally {` →
:1822 `_isDetecting = false;`). `finally` runs on every exit path including the
early `if (!mounted) return;` guards (:1659, :1667) and any thrown exception.
The pre-`try` guard at :1590 (`|| _isDetecting ||`) only *reads* the flag and
cannot strand it. The only way to strand `true` is an isolate/process crash, in
which case all per-instance state is moot.

**Гипотеза**: The prompt's concern is already addressed by the existing
try/finally. No stranded-flag bug exists.

**Тип**: verified_safe (not a bug). Documented here so the concern is closed
with evidence rather than re-raised.

## 2.3 Hungarian — verified_robust: edge cases handled

**Файл**: lib/tracker/hungarian.dart:30-131, 17

**Сценарий**: 2.3 (edge cases)

**Ожидание**: `dets.length == 0`, `tracks.length == 0`, mismatched dimensions,
and `kForbidden` cells must not crash or produce invalid assignments.

**Факт**:
- `rows == 0` → returns `const <int>[]` (:35).
- `cols == 0` → returns `List<int>.filled(rows, -1)` (:37) — all unassigned.
- `rows > cols` → internally transposed (:40-43) so the rectangular case is
  solved correctly.
- `kForbidden = 1e30` cells (:17) are always dropped from the result
  (:122-124), independent of `maxAssignableCost`.
- `maxAssignableCost` (strictly-exceeds) drops assignments above the threshold
  (:126-128).
- Test helpers `totalCost` (:153) and `isValid` (:167) exist for validation.

The tracker pre-fills the cost matrix with `kForbidden` and labels that don't
match skip the cell (tracker.dart:118), so cross-label assignments are
forbidden-by-construction. Harness B5 (15×15) solves without crashing.

**Гипотеза**: The solver is robust on all enumerated edge cases.

**Тип**: verified_robust (not a bug).

## 2.4 TtsService — risk: critical queue is unbounded; info is starved by design

**Файл**: lib/services/tts_service.dart:736-768, 777-825, 78-86, 21

**Сценарий**: 2.4 (queue starvation)

**Ожидание** (prompt): can a sustained `critical` stream block `info` forever?
Is there a max queue size / eviction policy?

**Факт**:
- On enqueue of a `critical` job, **all non-critical jobs are purged**
  (`_queue.removeWhere((j) => j.priority != SpeechPriority.critical)`,
  :739) and the critical is added; the critical branch `return`s at :768
  **before** the queue-cap logic.
- The queue cap (`_queue.length >= 4`, :777) with eviction
  (oldest info → oldest warning → drop incoming, :795-824) applies ONLY to
  warning/info jobs — **criticals bypass the cap entirely**.
- Critical dedup is by exact-text only (:740, :775); distinct-text criticals
  accumulate with no size limit. Age is bounded by stale pruning
  (`_kCriticalStaleAfter = 4 s`, :21; `_pruneStaleCriticals`, :78-86) but only
  if `_pump`/prune is called — a rapid stream of distinct-text criticals
  arriving faster than they are spoken grows the queue without bound.

**Гипотеза**: `info` (and `warning`) are starved under any sustained critical
stream — this is **by design** and is a declared safety inviolable (critical
preemption). The residual risk is the **unbounded critical queue** itself:
distinct-text criticals can pile up and be spoken long after the hazard passed
("stale hazard alert fires after the hazard is gone" — explicitly called out in
the project checklist). The 4 s stale-prune mitigates this only if pruning runs
between bursts.

**Тип**: risk (stale-critical aftershock). The starvation of info is
intended/safe; the unbounded distinct-critical growth is the actionable item.
Harness D1 confirms preemption; D2 confirms 4 s pruning works when invoked.

**Solution (NOT applied)**: Consider capping the critical queue (e.g. keep only
the N most-recent distinct-text criticals) and/or proactively pruning stale
criticals on each `say`. Do NOT weaken the `removeWhere != critical` preemption
(safety inviolable).

## 2.5 PerformanceThrottler — risk + incorrect_assumption: critical-thermal FPS

**Файл**: lib/utils/performance_throttler.dart:199-281; lib/models/constants.dart:358, 363, 382; lib/camera_screen.dart:2164

**Сценарий**: 2.5 / D20 (thermal throttling code path)

**Ожидание** (prompt): at `kThermalStatusCritical`, `_detectInterval` ≈
`kTargetFrameBudgetMs + kThermalPenaltyCriticalMs` = 140 + 120 = 260 ms →
1000/260 ≈ 3.8 FPS > `kMinAcceptableDetectFps = 3`.

**Факт**: The prompt's formula is **mechanically wrong**. `detectInterval`
(:199) computes `base = perfMs + thermalPenalty + motionBias + memoryBias`
(:248-250) but `base` is **not** the returned interval at critical. The
critical branch (:253-266) is a **burst/idle alternation**:
- Burst (first `_kThermalBurstFrames = 3` frames, :255-257):
  `requestedMs = max(batteryMs, perfMs + thermalPenalty ~/ 2)` ≈ 140 + 60 =
  **200 ms → ~5 FPS**.
- Idle (after 3 bursts, :258-265):
  `requestedMs = min(max(batteryMs, _kThermalIdleMs + base), kDetectIntervalSafetyCeilingMs)`
  = `min(max(batteryMs, 500 + 260), 500)` = **500 ms → 2.0 FPS**
  (walking, normal memory, healthy inference).
- Final clamp `min(requestedMs, kDetectIntervalSafetyCeilingMs = 500)` (:280).

So sustained critical-thermal detection runs at **2.0 FPS**, which is **below**
`kMinAcceptableDetectFps = 3` (333 ms ceiling). The two constants conflict:
`kDetectIntervalSafetyCeilingMs = 500` implies a 2 FPS floor, while
`kMinAcceptableDetectFps = 3` implies a 333 ms ceiling. The 3-frame burst
(~600 ms of 5 FPS) plus the ground-safety MiDaS pass every
`kCriticalThermalGroundSafetyIntervalMs = 5000` ms (:101,
`isGroundSafetyMidasDue` :92-95) partially mitigate, but steady-state is 2 FPS.

**Гипотеза**: At 1.5 m/s walking speed, 2 FPS = 500 ms between detections =
**0.75 m blind travel per gap**. A hazard appearing just after a detection
could be announced ~0.75 m closer than ideal. The burst covers the first
~0.9 m (3×200 ms × 1.5 m/s), and the 5 s ground-safety pass preserves curb /
step-down detection, but a moving vehicle entering mid-idle could be delayed.
This is a deliberate thermal-protection tradeoff, but the
`kDetectIntervalSafetyCeilingMs` vs `kMinAcceptableDetectFps` inconsistency
should be made explicit.

**Тип**: risk (steady-state 2 FPS < 3 FPS minimum) + incorrect_assumption (the
prompt's 3.8 FPS arithmetic does not match the code).

**Solution (NOT applied)**: Either reconcile the constants (raise
`kMinAcceptableDetectFps` awareness that critical-idle is intentionally 2 FPS,
or lower the safety ceiling) and add a TTS degradation notice when entering
critical-idle so the blind user knows detection has slowed. Do NOT remove the
thermal burst or ground-safety pass (safety inviolables).

## 2.6 GroundPlaneAnalyzer — note (NOT architectural_gap): stairs detection EXISTS

**Файл**: lib/utils/ground_plane_analyzer.dart:335-341, 911-1251; lib/utils/depth_hazard.dart:8

**Сценарий**: 2.6 / A5 (stairs)

**Ожидание** (prompt): "нет [stairs logic] → зафиксируй как
`ARCHITECTURAL_GAP: stairs_detection`."

**Факт**: The prompt's assumption is **incorrect** — stairs detection is
substantially implemented:
- `_detectStairsDown` (:917) computes a per-row median depth signal over cols
  48-208 / rows 64-256 (`_computeStairsSignal` :1144), differences it
  (stride 4), and classifies via autocorrelation (`_classifyStairsSignal`
  :1170): energy > 1e-4, directionality > 0.58, a peak at lag 12-48 with
  `peakAc >= 3 × acMean` and `peakAc > 0.18`.
- Public test helpers exist: `debugDetectStairsDown` (:335) and static
  `detectStairsDownFromMap` (:1248).
- An escalator-riding upgrade uses phase-shift between consecutive signals
  (`_findStairsPhaseShift` :1073) when the user is stationary
  (`_kEscalatorConfirmFrames = 2`, :963).
- `DepthHazardType.stairsDown` (depth_hazard.dart:8) is wired through
  `DepthPipelineController` (:280, :314) and `SceneNarrator` (:199) to the
  `hazard_stairs_down` trilingual strings (strings.dart).

Harness A5 confirms: a synthetic periodic descending-stairs map classifies as
`stairsDown` (score 0.95, cov 0.88); a smooth ramp and a single step both
return `null` (correct discrimination).

**Гипотеза**: There is no architectural gap to log. The detector relies on an
autocorrelation signature that synthetic data can reproduce; on-device
validation with real MiDaS stair depth is still warranted (the harness cannot
prove real-world recall). The many `_kStairs*` private thresholds
(:911-1141) are, like 2.1, **untested_assumption** (no rationale comments) but
they ARE empirically exercised by A5.

**Тип**: note (corrects the prompt). Sub-issue `untested_assumption` on the
`_kStairs*` thresholds — same class as 2.1.

## Cross-cutting harness findings (Phase 1, recorded for traceability)

  requires `gap >= kCriticalRepeatCooldownSafety = 2000 ms` even when the
  distance-drop condition (`candDistM <= lastDistM × 0.70`) is met. The prompt's
  "passes at 1000 ms" is impossible. Escalation is a **no-op for the 3 safety
  categories** (obstacleClose / corridorBlocked / approachingVehicle) whose base
  cooldown is already 2000 ms; it only relaxes default-cooldown categories
  (4000 ms → 2000 ms). `risk`: for the most safety-critical categories, a
  rapidly approaching object gets NO early re-alert from escalation — only the
  2000 ms cooldown gates it.
